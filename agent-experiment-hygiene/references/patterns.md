# Patterns and Anti-patterns

## Good patterns

### Pattern 1: Main agent as orchestrator

The main agent understands the whole experiment and delegates output generation or evaluation to subagents with controlled information.

Good when: the experiment needs coordination, file preparation, scoring, and a final summary.

### Pattern 2: Method runner subagents

Each method output is generated by a separate runner that sees only the information appropriate for that method.

Good when: comparing prompts, workflows, tools, skills, or baselines.

### Pattern 3: Baseline isolation

A baseline should not see the new method’s output, expected answers, or evaluation commentary.

Good when: asking “What would a normal LLM/agent do with only the original task?”

### Pattern 4: Blind evaluator

An evaluator sees anonymized outputs such as `output_1`, `output_2`, and `output_3`, not method labels.

Good when: judging human preference, readability, usefulness, or quality.

### Pattern 5: Auditor role

An auditor sees the full setup and checks whether the comparison conditions were fair enough for the claim.

Good when: the result will influence future work or be presented as evidence.

### Pattern 6: Holdout or variant cases

Keep some cases away from method design. Use them later to check whether the method overfit the known examples.

Good when: improving prompts or agent workflows based on a small corpus.

### Pattern 7: Repeated trials when variance matters

Run the same method multiple times when outputs may vary meaningfully.

Good when: comparing LLM outputs, brainstorming, extraction, review quality, or preference.

## Anti-patterns

### Anti-pattern 1: The author solves the test

The same agent designs the expected result, generates the candidate answer, and judges it.

Risk: self-confirming evaluation.

### Anti-pattern 2: Baseline sees the answer key

The baseline reads expected issues, previous reports, target outputs, or comparison goals.

Risk: contaminated baseline that is not representative.

### Anti-pattern 3: Blind evaluation with visible labels

Reports say “Formal result,” “baseline,” “new method,” or contain file names that reveal the method.

Risk: evaluator bias.

### Anti-pattern 4: Disappearing failures

Failed cases are removed, not reported, or converted into easier cases.

Risk: inflated performance.

### Anti-pattern 5: One example becomes a conclusion

One good output is used to claim the method works generally.

Risk: overclaiming.

### Anti-pattern 6: Provenance-free comparison

No record of what each runner saw.

Risk: impossible to audit.

### Anti-pattern 7: Overbuilding the experiment

A lightweight development check becomes a rigid, expensive framework.

Risk: the skill becomes too heavy to use.

## Decision guide

Use more rigor when:

- comparing methods;
- evaluating a baseline;
- making a product or design decision;
- results are surprising;
- the method has been tuned on known cases;
- humans will trust the conclusion.

Use less rigor when:

- debugging a known issue;
- doing a quick smoke check;
- exploring rough ideas;
- the cost of strict isolation exceeds the value of the result.
